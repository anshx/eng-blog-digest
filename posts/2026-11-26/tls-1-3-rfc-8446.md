# A Detailed Look at RFC 8446 (a.k.a. TLS 1.3)

## What's new to learn

1. **Transcript-bound authentication** — Every TLS 1.3 signature covers a hash of *all* handshake messages sent so far; an adversary cannot strip, substitute, or reorder any single message without invalidating the proof of identity.

2. **Authentication/key-exchange separation** — TLS 1.3 decouples *who you're talking to* (certificate + signature) from *what key you use* (ephemeral ECDHE); TLS 1.2's RSA key exchange fused the two in a way that destroyed forward secrecy.

3. **0-RTT via Pre-Shared Keys** — Resumption re-uses a symmetric ticket from a prior session, buying back one round trip at the explicit cost of replay-attack vulnerability and no forward secrecy for that first flight.

## Prerequisites

- What a digital certificate is and what a signature proves
- Diffie-Hellman key exchange at a conceptual level (two parties derive a shared secret without sending it)
- What "forward secrecy" means: recording today's encrypted traffic should not become decryptable if a long-term key leaks tomorrow

## The core idea

TLS 1.3 cuts the full handshake from two round trips to one by having the client include an ephemeral ECDHE public key in its very first message — before it even knows the server's choice of cipher suite. The server immediately computes the shared secret, derives handshake keys, and sends its full certificate chain plus a signature over the entire conversation-so-far, all encrypted. The client verifies everything and both sides are ready. No second round trip.

The signature does not just say "I own this certificate." It says "I own this certificate **and** I was present for this exact conversation, in this order, with these parameters." An adversary who records traffic cannot later replay a modified handshake — the signature would not verify.

## Mechanics

### The 1-RTT handshake

```
Client                                 Server
─────────────────────────────────────────────────────────────
ClientHello
  + key_share (ephemeral ECDHE pubkey)
  + supported_versions [TLS 1.3]
  ─────────────────────────────────────>
                                       ServerHello
                                         + key_share (server ECDHE pubkey)
                                       {EncryptedExtensions}
                                       {Certificate}
                                       {CertificateVerify}  ← signs transcript hash
                                       {Finished}
                                       <─────────────────────
{Finished}
[Application Data]
─────────────────────────────────────>
```

Curly braces `{}` denote messages encrypted under handshake traffic keys — the server's certificate is hidden from passive observers from the very first message exchange.

**Step-by-step:**

1. **ClientHello with key_share**: the client includes a fresh ECDHE public key (Curve25519 or P-256). In TLS 1.2 this came later; moving it to the first message is what makes 1-RTT possible.

2. **ServerHello + key_share**: the server picks a cipher suite and sends its own ephemeral ECDHE key. Both sides now compute the shared secret `Z = ECDH(client_priv, server_pub)`.

3. **Key schedule via HKDF**: TLS 1.3 uses a strict chain of HKDF-Extract and HKDF-Expand operations to derive every traffic key. The derivation chain is:

   ```
   early_secret       ← HKDF-Extract(0, PSK or 0)
        ↓
   handshake_secret   ← HKDF-Extract(early_secret, Z)
        ↓
   master_secret      ← HKDF-Extract(handshake_secret, 0)
   ```

   From each secret, labeled expansions produce distinct keys: `client_handshake_traffic_secret`, `server_handshake_traffic_secret`, `client_application_traffic_secret`, etc. Every key has a unique ASCII label (e.g., `"c hs traffic"`), so even if two inputs collide the outputs stay independent — **domain separation**.

4. **CertificateVerify**: the server signs the byte string:

   ```
   context_string || 0x00 || Transcript-Hash(ClientHello..Certificate)
   ```

   The transcript hash includes every handshake message so far. The 64-byte `context_string` (`"TLS 1.3, server CertificateVerify"`) prevents cross-protocol reuse of the same signature across TLS contexts.

5. **Finished**: a MAC over the full transcript using `finished_key = HKDF-Expand(handshake_secret, "finished")`. Both sides compute and verify it; this provides integrity over all handshake messages including those before the certificate.

### Why TLS 1.2 RSA key exchange killed forward secrecy

In TLS 1.2 RSA-RSA, the client encrypted a 48-byte `premaster_secret` under the server's RSA public key. Session keys were derived from this secret. An adversary who recorded the full session and later obtained the server's RSA private key could decrypt the `premaster_secret` and therefore derive every session key. Because RSA private keys are long-lived (years), every historical session was retroactively at risk.

TLS 1.3 forbids RSA key exchange entirely. The certificate's private key is used only to *sign* the transcript — never to *derive* keys. The session key comes from an ephemeral ECDHE exchange; the server discards its private value immediately after the handshake. Historical traffic remains safe even if the certificate is later compromised.

### 0-RTT resumption and its price

After a completed handshake the server sends a `NewSessionTicket` containing a PSK identifier (a resumption key encrypted under a server-side secret). On reconnect:

```
Client                                 Server
─────────────────────────────────────────────────────────────
ClientHello
  + psk_identity   (from previous ticket)
  + early_data_indication
[0-RTT Application Data]  ←── encrypted under early_traffic_key
─────────────────────────────────────>
                                       ServerHello
                                       ...
```

The first application-layer bytes travel in the same IP packet as the ClientHello — no round trips to establish the channel.

**The mandatory tradeoffs:**

| Property          | Full 1-RTT handshake  | 0-RTT resumption          |
|-------------------|-----------------------|---------------------------|
| Forward secrecy   | Yes (ephemeral ECDHE) | **No** (PSK is long-lived)|
| Replay protection | Yes                   | **No** (by design)        |
| Latency           | 1 RTT                 | 0 RTT                     |

RFC 8446 explicitly prohibits non-idempotent actions in 0-RTT data. Any server that processes 0-RTT requests must assume an adversary may replay that exact ClientHello + data to a different server replica.

### What TLS 1.3 removed (and why each was dangerous)

| Removed feature           | Attack it enabled                        |
|---------------------------|------------------------------------------|
| RSA key exchange          | Retroactive decryption of all sessions   |
| Static ECDH               | Same—server key was not ephemeral        |
| CBC cipher suites         | POODLE, BEAST, Lucky Thirteen            |
| RC4                       | Statistical biases exploitable in hours  |
| SHA-1 for signatures      | Collision attacks                        |
| TLS compression           | CRIME (chosen-plaintext compression oracle) |
| Renegotiation             | Triple Handshake attack                  |
| Export cipher suites      | FREAK, Logjam                            |

TLS 1.3's cipher suite list is exactly five entries: AES-128-GCM-SHA256, AES-256-GCM-SHA384, ChaCha20-Poly1305-SHA256, AES-128-CCM-SHA256, AES-128-CCM-8-SHA256. No negotiation of hash functions, key sizes, or cipher modes; the whole list fits in one screen.

### Middlebox compatibility mode

TLS 1.3 deliberately impersonates TLS 1.2 on the wire. The `ClientHello.legacy_version` field says `0x0303` (TLS 1.2). There is a spurious `ChangeCipherSpec` message inserted after `ServerHello` even though it has no meaning in TLS 1.3. These are concessions to stateful middleboxes (deep packet inspection proxies, enterprise firewalls) that crashed or dropped sessions with an unknown version number.

The actual version is negotiated through the `supported_versions` extension, which broken middleboxes ignore.

## Where it breaks

1. **0-RTT replay**: An adversary at the network layer can capture and re-send the initial ClientHello + 0-RTT data to any replica of the server. Server-side single-use ticket tracking requires coordination across replicas; most deployments accept the risk for idempotent reads and block it for mutations.

2. **0-RTT no forward secrecy**: If the server's PSK database is compromised, all 0-RTT data ever sent under those tickets is decryptable. The PSK is a long-lived symmetric secret, not an ephemeral value.

3. **Client certificate privacy**: The server's certificate is encrypted; the client's certificate (mutual TLS) is also encrypted (sent after the client processes the server's Finished). But enterprise TLS inspection proxies that terminate and re-originate TLS see only the outer session; mTLS client identity is invisible to them.

4. **KeyShare prediction cost**: The client guesses the server's preferred ECDHE group and sends a key share for that group. If the server selects a different group, it sends a `HelloRetryRequest` and the handshake costs 2 RTTs after all. In practice, `x25519` is almost universally supported, making misprediction rare.

## Why it works

### Transcript hash = Fiat-Shamir for network protocols

The Fiat-Shamir transform converts an interactive proof (prover–verifier back-and-forth) into a non-interactive one by replacing the verifier's random challenges with a hash of the transcript so far. TLS 1.3's `CertificateVerify` is exactly this: instead of the verifier sending a random nonce and the server signing it, the server signs the hash of everything that has been said. Because the entire handshake is covered, the server cannot substitute different parameters and reuse a valid signature. This is the same technique that makes zk-SNARKs non-interactive and that makes Schnorr signatures batch-verifiable.

### Key exchange separation enables forward secrecy

TLS 1.3 makes forward secrecy a **structural consequence** rather than an optional mode. The session key depends on a discarded ephemeral ECDHE value. The certificate key is used for signing only. No amount of future key compromise can reach a past session because the material that produced the session key no longer exists. The same design appears in SSH (host key authenticates; DH exchange produces the session key), in Signal's Double Ratchet (ratchet key provides PFS; identity key provides authentication), and in the Noise Protocol Framework's `IK` and `XX` patterns.

### HKDF domain separation prevents cross-context confusion

Every key derived in TLS 1.3 carries a unique human-readable label string. Two derivation paths that happen to produce the same input bytes will produce different output keys if their labels differ. This defeats "unknown key share" attacks where an adversary tricks a party into proving ownership of a key in a context different from the intended one. The same label-based separation appears in BLAKE3's tree/leaf node domain separation, in HMAC-DRBG's "personalization strings," and in AWS KMS context fields.

## Going deeper

1. **RFC 8446** — the full TLS 1.3 specification, unusually clear for an RFC, with its own design rationale in Appendix E: https://www.rfc-editor.org/rfc/rfc8446
2. **The Illustrated TLS 1.3 Connection** (tls13.ulfheim.net) — an annotated packet capture that walks through every byte of a real TLS 1.3 handshake, labeling each HKDF derivation and key usage
3. **"A Cryptographic Analysis of the TLS 1.3 Handshake Protocol" (Dowling, Fischlin, Günther, Stebila)** — proves that TLS 1.3's design achieves the strongest formal security model for key exchange (multi-stage key exchange with channel binding), and explains exactly why each removed feature was necessary for the proof to go through
